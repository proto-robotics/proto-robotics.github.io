Proposal · revision 5 · for review

A new set of blocks, designed around the new make.

The new make asks every motor call how long to run: some seconds, some degrees, or a twentieth of a second inside a loop. This plan replaces the editor's blocks with ones that say that on their face, and adds the board's buttons, lights and encoders.

  2. Decide P0 first, above all P0.2, the "step" blocks that only belong inside loops.
  3. About 9 working days, and the motor blocks run on the board after day 4.

Part 1 · Why

What this is for

The editor's blocks were made for the old make, where Spin started a motor and Stop ended it. In the new make a motor call runs for a set time and then stops the motor. Without a time it runs for 0.05 seconds. Patching the old blocks would leave words on them that no longer match what the board does.

So the blocks start again from make's own model. A motion block runs for some seconds, or through some degrees, or for one short step inside a loop. Buttons and lights come built into the board, so they are a letter in a dropdown with nothing to set up. Motors and drivetrains are still set up in the Devices pop-up.

Three ways to run a motor, and the block for each

Every motion block says how long it runs. The step block has a dashed edge and only fits inside a loop.

The ideas the whole plan rests on. If one of them is wrong, the rest gets rewritten.
  1. Each block writes one make call, so the Python in the code drawer reads like make's own docs.
  2. A motion block always shows how long it runs. A kid never has to know that 0.05 seconds is the default.
  3. Directions are words, forward and backward or left and right. Power runs from 0 to 100, never below.
  4. Old block programs are not converted. The blocks change too much for a converter to be worth its cost.

What it costs, and what you see first

About 9 working days. The step blocks worry me most. They are the one new idea kids have to learn. Prototype X2 showed Blockly can keep them inside loops, so the risk left is whether kids get the idea. The motor and drivetrain blocks run on the bench board after about day 4.

P0

The rules for the block set

Not code. Each one is a rule every block in P1 and P2 follows.

Takesone sitting AfterX1 to X3
  • P0.1One timed block per motion, with a seconds/degrees dropdown. "for [2] [seconds ▾]" switches to _degrees calls; Curve is the exception, with its own degrees block.
    Why
    Half the blocks of separate "for seconds" and "degrees" versions, and the two ways of measuring sit side by side.
    1. Dropdown. One timed block per motion; "for [2] [seconds ▾]" switches to degrees. Fewest blocks.
    2. Separate blocks. A "for N seconds" block and a "N degrees" block for each motion: 4 more blocks, each one plain sentence.
    3. Seconds only for now. Timed blocks in seconds; degree blocks in their own Encoder category.
  • P0.2Step blocks run one short step and only belong inside loops. A step Spin, Drive, Turn and Curve, with a dashed edge, for Forever, Repeat and Repeat until.
    Why
    It is how make keeps a motor going while the program checks a button, and how two motors run at once.
    1. Step blocks. A dashed step block for each motion, kept in loops by connection checks if X2 passes, by a linter error if not.
    2. "Until" blocks. "Spin arm forward at 50 power until [condition]" writes the loop itself. Nothing new to teach, but no way to run two motors or flash a light in the same loop.
    3. Both. Step blocks for loops, plus "until" blocks for the simple one-motor case. Easiest start, most blocks.
  • P0.3Directions are words, and power runs from 0 to 100. forward/backward on Spin and Drive, right/left on Turn; negative power is gone.
    Why
    "Spin forward at -50" was the most confusing thing in the old set.
    1. Words, 0 to 100. forward/backward and right/left dropdowns; power never below 0. Curve keeps -100 to 100 per side.
    2. Numbers only. No direction dropdown; power from -100 to 100 as make takes it, so -50 means backward.
    3. Words and negatives. The direction dropdowns, and power can still go below 0, which flips the direction again.
  • P0.4Stop offers brake or coast, braking by default. "Stop [arm] and [brake ▾]" writes brake(); "coast" writes stop().
    Why
    Brake and coast are the words robots use. Kids expect Stop to stop, and make's stop() coasts. make has no hold, so hold stays out.
    1. Brake by default. "Stop [arm] and [brake ▾]", with coast as the other choice.
    2. Coast by default. As make's stop() does; brake is the other choice.
    3. Two blocks. A "Brake [arm]" block and a "Coast [arm]" block, no Stop.
  • P0.5Buttons and lights are dropdowns of the board's names. A to D and L1, L2, with no set-up block and nothing in Devices.
    Why
    make builds them at start-up as button_a to button_d, light_l1 and light_l2.
    1. A to D. All four buttons. A starts the program, and pressed() works on it after.
    2. B to D. Leave A out, so the start button never doubles as an input.
  • P0.6Programs start with "from make import *". No make. prefix anywhere, as in make's docs.
    Why
    button_a.pressed() reads better than make.button_a.pressed().
    1. from make import *. No make. prefix, as in make's docs. The linter refuses device names make already uses.
    2. import make. Keep the make. prefix: longer lines, no name clashes.
  • P0.7Old block programs are not converted. Opening one says it was made with the old blocks, keeps a copy, and starts empty.
    Why
    A converter for blocks that changed meaning costs 2 days and guesses at what the kid meant.
    1. Message and a copy. Say it was made with the old blocks, keep a copy in local storage, start empty.
    2. Load what it can. Keep the blocks that still exist and drop the rest. Quicker, but a half program confuses.
    3. Convert. Turn old blocks into new ones: about 2 days, and it guesses at what the kid meant.

Risks, ranked

  • R1proto-learn breaks when it takes this build. Its lessons, diagrams and stored programs name the old blocks. Keep proto-learn on the current build until it gets its own pass.
  • R2Step blocks may confuse kids; we try them anyway. Blockly keeps them inside loops (X2). If kids struggle in class, "Spin until" blocks are the fallback.
  • R3make's API moves again before release. It is "Unreleased" on casper. P3.1's script keeps the line editor cheap to redo; each block is one call, so a rename is one line.
  • R4Kids lose saved block programs. P0.7 keeps a copy and says so. Their Python files still open in the line editor.

Accept a risk to say "understood, proceed". Reject to say "this needs a mitigation task before we start", and name it in the note.
